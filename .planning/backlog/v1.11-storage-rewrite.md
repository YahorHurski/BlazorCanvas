# v1.11 backlog — Storage model rewrite (anchor + geometry JSON)

**Status:** SCOPED, NOT STARTED. Design-complete after a discussion on 2026-07-23. **Essence: a
database model change + the code changes that flow from it — NO new user-facing features, no UI
work beyond what the storage change forces.** When starting, amend `docs/DECISIONS.md`
(+ PROJECT.md + `.planning/intel/`) with the decisions below **by name**, then run
`/gsd-new-milestone`.

**Prerequisite:** v1.1 shipped (canvas 1472×828 · selection UX + restyle · no-JS rule removed).

**⚠️ Ordering — v1.11 comes BEFORE v1.2.** The v1.2 backlog (`v1.2-figures-and-toolbar.md`) is written
entirely against the OLD "four integers = the bounding box" model (D-22) — its whole *"architectural
finding"* is that new shapes ride the 4-int bbox for free. **v1.11 reverses that model.** After v1.11
lands, the v1.2 backlog must be revised: new shapes will store as **geometry JSON**, not a bbox, and
the generic move/clamp reasoning there no longer applies as written. Do v1.11 first *because* it makes
v1.2's figures trivial (arbitrary shapes fit a JSON blob; they never fit 4 integers cleanly).

---

## Goal

Replace the four-integer bounding-box storage (`x1,y1,x2,y2`) with an extensible
**anchor (`x,y`) + geometry-JSON** model, so future figure types need **no schema changes**.
Existing figures are **preserved via a data migration**. The canvas-edge clamp is dropped. This is a
storage rewrite and its downstream code churn — nothing more.

## Why now (motivation)

The 4-integer model (D-22) only fits shapes expressible as a bounding box. v1.2's figures (star,
arrows, polygons) don't fit 4 integers cleanly. A `jsonb` geometry column holds any future shape with
zero `ALTER TABLE`. The anchor/geometry split also makes **drag touch only 2 columns** for any shape
(the form is stored relative to the anchor and never changes on move).

## The new schema (canonical)

```sql
CREATE TABLE users (            -- UNCHANGED
    id       integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username text NOT NULL UNIQUE,   -- lowercased, trimmed (D-44)
    password text NOT NULL           -- PLAINTEXT, throwaway only (D-08)
);

CREATE TABLE figures (
    id       uuid    NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,  -- order carried by z, not id
    user_id  integer NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    type     text    NOT NULL CHECK (type IN ('line','rectangle','circle','triangle')),
    x        integer NOT NULL,       -- anchor X
    y        integer NOT NULL,       -- anchor Y
    geometry jsonb   NOT NULL,       -- shape relative to anchor: circle {r}, rect {w,h}, ...
    z        numeric NOT NULL        -- layer order; NO UNIQUE; fractional (insert-between = midpoint)
    -- no created_at
    -- no DB CHECK on geometry (server is the sole writer; validated in code by construction)
);

CREATE INDEX ix_figures_user_id_z ON figures(user_id, z);   -- serves WHERE user_id + ORDER BY z

-- Load: SELECT * FROM figures WHERE user_id = @id ORDER BY z, id;
```

## KEY DECISIONS (resolved 2026-07-23)

1. **Two tables, still no `canvases`** (D-12 upheld). One canvas per user (D-03 upheld). Adding
   multi-canvas later is a cheap additive migration (new table + `figures.canvas_id` + backfill +
   switch load/sync scope from `user_id` to `canvas_id`); the expensive parts (canvas-management UI,
   per-canvas sync scoping) are unavoidable whenever done, so the empty table is not added now.
2. **`figures.id` → `uuid`** (was sequential `integer`). Order is now carried by `z`, so the id no
   longer needs to encode creation order — D-39's objection to UUID is thereby removed.
3. **Anchor + geometry split.** `x, y` are separate **integer** columns (D-20 upheld — pixels at 1:1,
   sub-pixel invisible; no zoom planned). Shape lives in `geometry jsonb`, **relative to the anchor**.
   Drag updates **only `x, y`** for any shape.
4. **`z` is `numeric`, NO `UNIQUE`** (fractional indexing: insert a layer = midpoint `(a+b)/2`,
   forever, no renumbering; `numeric` — arbitrary precision — never runs out, unlike float). Load
   `ORDER BY z, id`. There is no user-facing z-order control yet (D-04) — `z` exists so future
   front/back is a data op, not a schema change.
5. **`created_at` dropped everywhere** (D-46 upheld, new reason: order is `z`, no timestamp is read).
6. **Canvas-edge clamp REMOVED** (D-24, D-29, D-36 dropped). Figures may be dragged off-canvas.
   **Accepted risk, conscious:** an off-canvas figure is currently unrecoverable (no pan/undo) — taken
   because the roadmap intends to remove canvas bounds entirely later. Dropping the clamp is *what
   lets* the drag loop stay shape-agnostic without a stored bbox.
7. **Degenerate-draw guard KEPT, code-side** (`MinSizeGuard` in `Home.razor`'s commit path; D-23 #1,
   D-32 upheld). Rejects only **strictly zero-size** draws (invisible + unselectable = a permanent
   poison row), not merely small ones. Runs on C# primitives *before* geometry is serialised.
8. **`type`: keep `text` + CHECK whitelist (Variant 1).** DB keeps rejecting unknown types
   (belt-and-braces, most valuable *through the backfill* — see risks). Adding a future type costs one
   small alter-constraint migration, riding along with the code that type needs anyway. A **`canvases`
   lookup / `figure_types` table was rejected** — a new type always needs a code deploy (renderer,
   handler, button, geometry shape), so the "add a row not a migration" benefit is illusory, and it's
   the pointed-at ceremony table D-12 warns against.
9. **No DB CHECK on `geometry`.** The server is the only writer (D-09) and validates by construction;
   a jsonb CHECK would be per-type ugliness guarding only manual SQL / bad migrations.
10. **Index `(user_id, z)`** replaces the plain `ix_figures_user_id` — covers both the load filter and
    the `ORDER BY z`, so no separate sort step. No index on `geometry` or `type` (never queried into).

## Downstream code changes (the "вытекающие изменения")

- **`Figure` entity:** drop `X1/Y1/X2/Y2`; add `X`, `Y`, `Geometry`, `Z`; `Id` `int → Guid`.
- **`CanvasDbContext.OnModelCreating`:** new columns; **remove** the three geometry CHECKs
  (`circle_is_a_circle`, `box_is_a_box`, `line_is_a_line`); **keep** `figures_type_is_known`; map
  `geometry` to `jsonb`; composite index `(user_id, z)`; rewrite the table `COMMENT`.
- **New EF migration + DATA BACKFILL (preserve rows).** Auto-generated migration handles the schema
  delta; the row transform `x1,y1,x2,y2 → x,y,geometry` per type is **hand-written** (one
  `migrationBuilder.Sql(...)` or a one-off C# pass — decide at plan time). Must be **tested against the
  immutable fixture** `tests/.../Fixtures/v1.1-pre-rewrite.sql` + its `...-MANIFEST.md` expected values.
- **Persistence layer:** `Figures` provider — `InsertAsync` (build geometry + assign `z`),
  drag `UpdateAsync` (write `x,y` only), load query `ORDER BY z, id`.
- **Render:** `FigureShape.razor` reads `x1..y2` today → read `x, y, geometry`.
- **Draw / drag:** remove the D-36 clamp formula from the pointer handlers; drag translates the anchor
  (`x,y`) only. Re-express **normalisation (D-41)** for the new model (e.g. rectangle anchor = min
  corner + positive `{w,h}`; line anchor = left endpoint + `{dx,dy}` with either-sign `dy` — the
  "swap the whole point pair, never sort axes" landmine carries over).
- **Sync contract (D-53):** `SyncMessage` currently carries `Box(X1,Y1,X2,Y2)` (see `Home.razor`
  `SyncMessage.Move/Draw`, `ApplyMessage`) — **rework the payload to anchor + geometry**. Keep D-40
  (move is UPDATE-only), D-54 (mid-drag discard), D-47 (throttle) semantics intact.
- **Tests:** `SchemaShapeTests` (constraint/shape assertions) rewritten to the new schema; edge-clamp
  tests removed/repurposed; add the migration round-trip test against the fixture. TEST-01's three
  silent-failure tests re-evaluated (the circle round-trip becomes a `{r}` assertion).

## The risk we accepted on Variant 1 vs the alternatives (recorded so it stays conscious)

Keeping the `type` CHECK (Variant 1) is belt-and-braces because the server is the sole writer. It was
kept — rather than dropped (Variant 2) — chiefly because this milestone **preserves data via a bulk
backfill**, and a bulk transform over every row is exactly where the CHECK turns a buggy migration into
an immediate rollback instead of silent corruption across all users. If `type` is later modelled as a
**C# enum**, the app-path risk of an invalid type largely disappears and dropping the CHECK could be
revisited — but not during the migration.

## Decisions to amend WHEN v1.11 STARTS (not before)

- **D-22 — SUPERSEDED.** Four-integer bbox → **anchor `x,y` + `geometry jsonb`**; a circle is stored as
  `{r}` (a single scalar — an oval is structurally unrepresentable, even stronger than the inscribed
  square). The whole "raw columns must BE the bbox" rationale dies with the edge clamp (D-24).
- **D-39 — SUPERSEDED.** `id` `integer` (= z-order) → `id uuid`; order carried by explicit `numeric z`.
- **D-24 / D-29 / D-36 — DROPPED.** No canvas-edge clamp; figures may leave the canvas.
- **D-53 — AMENDED.** Sync payload → anchor + geometry (D-40/D-47/D-54 semantics unchanged).
- **D-46 — AMENDED.** `created_at` stays dropped; `type text` + whitelist CHECK **kept** (Variant 1).
- **D-23 — AMENDED.** Guard #1 (reject degenerate) stays, code-side; guard #2 ("never clamp
  individually") is **moot** — there is no clamp.
- **D-41 — REVISIT.** Per-type normalisation re-expressed for anchor+geometry (line swap-pair rule
  carries over; box "sort axes" becomes "positive `{w,h}`").
- **D-20 — UPHELD.** `x, y` stay `integer`.
- **D-12 / D-03 — UPHELD.** Two tables, one canvas per user — but every `figures` column is replaced.
- **NEW decision entry:** the anchor+geometry model, `uuid` id, `numeric` fractional `z`, composite
  `(user_id, z)` index, and "no DB CHECK on geometry / server is sole writer" trust boundary.
- **Cross-milestone:** revise `v1.2-figures-and-toolbar.md` — its 4-int-bbox premise no longer holds.

## Left for plan / spec time (not milestone-scoping decisions)

- Exact **JSON shape per type** — e.g. `circle {r}`, `rectangle/triangle {w,h}`, `line {dx,dy}`
  (anchor = one endpoint). Especially pin the **line** representation explicitly.
- **`z` assignment formula** — append (`max(z) + step`) vs insert-between (midpoint).
- **`uuid` v4 vs uuidv7** — v7 is time-ordered → a *meaningful* `ORDER BY z, id` tiebreak
  (later-created on top) and better index locality; v4 (`gen_random_uuid()`) is the simple default.
- Whether `Figure.Type` becomes a **C# enum** (mapped to `text`).
- **Backfill implementation** — `migrationBuilder.Sql` vs a one-off C# pass.
